# INVEST / SMART — バックログ品質の判定

PBI（ストーリー）は INVEST、ストーリーを分解したタスクは SMART を満たすように書く。作成・分割・レビューのいずれでも、成果物に判定結果を添える。

## INVEST（ストーリー向け）

| 項目 | 判定の問い | NG の兆候 |
|---|---|---|
| **I**ndependent | 他のストーリーと概念が重ならず、どの順番でも着手できるか | 「A が終わらないと B ができない」が連鎖している。同じ画面・同じ仕様を複数ストーリーで取り合っている |
| **N**egotiable | 実装の詳細ではなく、要求の本質を書いているか | 画面レイアウトやテーブル定義まで確定済みで、議論の余地がない。詳細は開発中に顧客と開発者が一緒に詰めるもの |
| **V**aluable | 顧客（利用者）にとっての価値が分かるか | 「DB層を作る」「API を用意する」など、利用者から見て価値のない技術層だけのストーリー |
| **E**stimable | チームが見積もり、優先順位を付けられるほど理解できているか | 未知が大きすぎて見積もれない。見積もれないのは、たいてい Negotiable が足りないか、大きすぎる |
| **S**mall | 長くても数人週で終わる大きさか | 「1か月以上かかる」。これは「全体像を理解できていない」の言い換えであることが多い |
| **T**estable | テストを書けるほど明確か（受け入れ条件を書けるか） | 「使いやすくする」「速くする」など、完了を判定できない表現 |

### 分割の指針
- **縦に切る**。UI〜ロジック〜データを貫く薄い一切れにし、どの一切れも単独で価値を届けるようにする（「ケーキ全体の本質を一切れで」）。
- **層ごとに横に切らない**（「画面だけ」「API だけ」「DB だけ」）。横に切ると Valuable と Independent が崩れる。
- Estimable で詰まったら、まず調査用のストーリー（スパイク）を切り出して未知を減らす。

## SMART（タスク向け）

| 項目 | 判定の問い |
|---|---|
| **S**pecific | 何をするかが具体的で、誰が読んでも同じ作業を思い浮かべるか |
| **M**easurable | 終わったかどうかを判定できるか |
| **A**chievable | 担当者が実行できるか（必要な権限・知識・前提がそろっているか） |
| **R**elevant | 親ストーリーの達成に寄与しているか |
| **T**ime-boxed | 期限、または作業時間の上限があるか |

## 出力形式

PBI ごとに次の形で出す。

```markdown
### <PBI タイトル>
<ユーザーストーリー: 〈誰〉として、〈何〉をしたい。それは〈なぜ〉だから。>

受け入れ条件:
- ...

| I | N | V | E | S | T |
|---|---|---|---|---|---|
| ○ | ○ | △ | ○ | × | ○ |

- △/× の理由と修正案（× があれば分割案を出す）
```

- 判定は ○（満たす）／△（懸念あり）／×（満たさない）の 3 段階で付ける。
- △ と × には必ず理由を書く。全部 ○ のときは表だけでよい。
- タスクまで分解した場合は、各タスクに SMART を同じ形式で添える。
- 判定に必要な情報（利用者、価値、受け入れ条件など）が足りないときは、推測で埋めず質問する。
